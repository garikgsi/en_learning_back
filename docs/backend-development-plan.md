# План разработки backend English Learning

## 1. Цель и границы первой версии

Создать JSON API `/api/v1` для существующего Vue/Capacitor-клиента:

- регистрация, вход, обновление и отзыв сессии;
- получение и изменение профиля;
- загрузка аватара;
- словарь с поиском, сортировкой и пользовательской статистикой;
- очередь ручного повторения;
- создание и идемпотентное завершение упражнения.

Синхронизацию настройки `dictionaryWordsPerPage`, удаление записи из очереди
повторения и назначение маршрутного `code` предлагается не включать в MVP до
уточнения требований.

## 2. Результаты анализа фронтенда

### Что уже зафиксировано UI

- Телефон российский, в API передаётся как `+7XXXXXXXXXX`.
- PIN состоит ровно из четырёх цифр.
- Имя после `trim()` содержит минимум два символа.
- Аватар необязательный, только изображение до 2 МБ.
- Словарь ищется одновременно по русскому и английскому тексту.
- Допустимая сортировка: `russian`, `english`, `repeatCount`.
- Фразу можно добавить вручную, но нельзя выбрать автоматически.
- Каждая словарная запись выполняется в направлениях `en` и `ru`.
- Ручное добавление слова должно быть идемпотентным.
- Повторное завершение одной exercise session не должно менять статистику.

### Расхождения и риски

1. Стандартная Laravel-модель использует email/password и bigint ID, а клиент
   использует телефон/PIN и строковый ID пользователя.
2. Поле `email` есть в `UserInfo`, но UI его не запрашивает и не показывает.
3. `isSelectedForRepetition` описан в контракте, но отсутствует в текущем
   TypeScript-типе `DictionaryWord`.
4. Регистрация и профиль сейчас передают аватар как base64. Серверу нужен
   бинарный `multipart/form-data`.
5. `/exercises` не передаёт `code`; только устаревающий маршрут `/:code?`
   вызывает `loadWords(code)`.
6. При текущем алгоритме выбираются все записи с минимальным `repeatCount`.
   При большом словаре упражнение может получиться неограниченного размера.
7. К событию `finish` фронтенд повторяет проблемное слово, пока `isOk` не станет
   `true`. Следовательно, один `isOk` не определяет успешность статистики.
8. Клиентская авторизация теряется при перезагрузке: нет bootstrap-запроса и
   безопасного постоянного хранения токенов.
9. В `src/pages/index.vue` находятся похожие на реальные реквизиты БД. Их нужно
   удалить, а пароль сменить, если он когда-либо использовался.
10. Демонстрационные `repeatCount` во frontend являются фиктивными и не должны
    импортироваться как пользовательская статистика.

## 3. Предлагаемые архитектурные решения

### API и код

- Версионированные маршруты в `routes/api.php`.
- Тонкие controllers; бизнес-правила в Actions/Services.
- Валидация через отдельные Form Request.
- Ответы через API Resources.
- Авторизация и доступ к сущностям через middleware и policies.
- Единый JSON-формат ошибок и middleware для `requestId`.
- Все даты возвращаются в ISO 8601 UTC.
- OpenAPI-файл является фиксированным контрактом для backend и frontend.

### Авторизация

Для общего поведения web SPA и Capacitor рекомендуется Bearer-схема:

- случайный opaque access token на 15 минут;
- refresh token на 30 дней;
- в БД хранятся только хэши токенов;
- refresh token ротируется при каждом обновлении;
- logout отзывает текущую сессию;
- refresh endpoint: `POST /api/v1/auth/refresh`;
- клиент хранит refresh token в защищённом хранилище устройства, не в
  `localStorage`.

PIN хэшируется Argon2id. Из-за пространства всего в 10 000 комбинаций дополнительно
нужны отдельный серверный pepper, rate limit и временная блокировка перебора.

### Аватары

Регистрацию выполнять JSON-запросом без аватара. После успешной регистрации
клиент при необходимости вызывает `PUT /users/me/avatar` multipart-запросом.
Сервер проверяет MIME и декодирование, удаляет metadata, ограничивает размеры,
конвертирует изображение в WebP и хранит через Laravel Filesystem.

## 4. Проект схемы PostgreSQL

### `users`

- `id` UUIDv7, primary key;
- `phone` varchar, unique, в E.164;
- `name`;
- `pin_hash`;
- `avatar_path`, nullable;
- `created_at`, `updated_at`;
- email не хранить в MVP.

### `auth_sessions`

- UUIDv7 `id`, `user_id`;
- `access_token_hash`, `refresh_token_hash`, оба unique;
- `access_expires_at`, `refresh_expires_at`;
- `last_used_at`, `revoked_at`;
- необязательные `device_name`, `ip_address`, `user_agent`;
- индексы по пользователю, срокам действия и активным токенам.

### `dictionary_entries`

- bigint `id`;
- `english`, `russian`;
- `is_phrase`;
- unique по паре нормализованных значений;
- trigram GIN-индексы PostgreSQL для регистронезависимого substring-поиска;
- согласованная ICU-collation для сортировки русского и английского текста.

### `user_word_stats`

- `user_id`, `dictionary_entry_id`, составной unique/primary key;
- `successful_repeat_count`;
- `failed_repeat_count`;
- `last_repeated_at`;
- `repeat_count` не хранить отдельно, а вычислять как сумму двух счётчиков.

Отсутствующая строка статистики эквивалентна нулевым счётчикам.

### `user_repetition_items`

- `user_id`, `dictionary_entry_id`, составной unique;
- `selected_at`;
- запись удаляется/помечается обработанной только по согласованному правилу.

### `exercise_sessions`

- UUIDv7 `id`, `user_id`;
- статус `active|completed|expired`;
- `code`, nullable до определения назначения;
- `created_at`, `expires_at`, `completed_at`;
- fingerprint принятого результата для безопасной идемпотентности.

### `exercise_session_items`

- `exercise_session_id`, `dictionary_entry_id`;
- snapshot `english` и `russian`, чтобы изменение словаря не меняло сессию;
- `position`, `was_manually_selected`;
- unique по session и dictionary entry.

### `exercise_results`

- `exercise_session_item_id`;
- направление `en|ru`;
- `retries`, `skip_times`, `hint_times`, `error_times`;
- итоговая серверная классификация `is_successful`;
- unique по item и direction.

`variants` валидировать, но в MVP не сохранять: они не нужны для статистики и
могут содержать пользовательские данные.

## 5. Этапы работ

### Этап 0. Зафиксировать продуктовые решения

1. Подтвердить авторизацию и сроки токенов.
2. Утвердить размер упражнения и порядок выбора при равных счётчиках.
3. Утвердить формулу успешного повторения и увеличение счётчиков.
4. Определить жизненный цикл ручной очереди.
5. Решить судьбу `code`, email и настройки количества строк.
6. Зафиксировать OpenAPI v1 и примеры ошибок.

**Готово, когда:** спорные поля и бизнес-правила больше не требуют трактовки
backend-разработчиком.

### Этап 1. Backend foundation

1. Добавить `routes/api.php` и группу `/api/v1`.
2. Настроить CORS для web-origin и разрешённых Capacitor origins.
3. Реализовать общий error envelope и `requestId`.
4. Добавить базовые API Resources, health/readiness checks.
5. Подключить Pint, Larastan/PHPStan и CI для PostgreSQL.
6. Создать OpenAPI skeleton и правила версионирования.

**Проверки:** JSON для всех API-ошибок, CORS-тесты, CI запускает lint, static
analysis и PHPUnit.

### Этап 2. Пользователи и авторизация

1. Заменить стандартную users migration на телефон/PIN/UUIDv7.
2. Создать `auth_sessions`.
3. Реализовать:
   - `POST /auth/register`;
   - `POST /auth/login`;
   - `POST /auth/refresh`;
   - `POST /auth/logout`;
   - `GET /users/me`.
4. Нормализовать и валидировать телефон.
5. Добавить Argon2id + pepper, rate limits, блокировку перебора и отзыв сессий.

**Проверки:** успешные сценарии, дубликат телефона, неверный PIN, rate limit,
истечение/ротация/reuse refresh token, logout и доступ к закрытым endpoint.

### Этап 3. Профиль и аватар

1. `PATCH /users/me`.
2. `PUT /users/me/pin` с обязательным текущим PIN.
3. `PUT /users/me/avatar` multipart.
4. Публичная выдача либо подписанные URL для аватара.
5. Удаление старого файла только после успешной записи нового.

**Проверки:** MIME spoofing, размер >2 МБ, повреждённое изображение, смена PIN,
rollback при ошибке storage.

### Этап 4. Словарь

1. Создать `dictionary_entries` и `user_word_stats`.
2. Перенести 74 демонстрационные пары из frontend в versioned seeder/import,
   но начать пользовательские счётчики с нуля.
3. Реализовать `GET /dictionary` с allowlist сортировки, limit/offset и total.
4. Добавить `isSelectedForRepetition` через связь текущего пользователя.
5. Настроить и проверить русский/английский поиск и сортировку.

**Проверки:** поиск в обоих языках, регистр, `%/_`, пустой запрос, граничные
limit/offset, сортировка, отсутствие утечки чужой статистики.

### Этап 5. Ручная очередь повторения

1. Создать `user_repetition_items`.
2. Реализовать идемпотентный `POST /repetition-list/words`.
3. Разрешить ручное добавление слов и фраз.
4. При необходимости добавить `DELETE`, но только после изменения UI.

**Проверки:** повторное добавление, неизвестный wordId, параллельные запросы,
изоляция пользователей.

### Этап 6. Exercise sessions

1. Создать session, items и results migrations/models.
2. Реализовать транзакционный выбор:
   - сначала активная ручная очередь;
   - затем только не-фразы с минимальной статистикой;
   - заполнение до согласованного лимита;
   - snapshot состава сессии.
3. Реализовать `POST /exercise-sessions`.
4. Реализовать `POST /exercise-sessions/{id}/complete`:
   - session принадлежит текущему пользователю;
   - IDs и направления точно соответствуют snapshot;
   - нет дубликатов и отрицательных счётчиков;
   - транзакция с row lock;
   - повторный идентичный запрос возвращает прежний результат;
   - конфликтующий повторный payload возвращает `409`.
5. Атомарно обновлять статистику и ручную очередь.
6. Добавить срок жизни и очистку брошенных сессий.

**Проверки:** конкурентное завершение, повторная отправка, подмена wordId,
неполный/дублированный результат, чужая/истёкшая сессия, rollback.

### Этап 7. Интеграция frontend

1. Сгенерировать/зафиксировать TypeScript DTO из OpenAPI.
2. Добавить единый HTTP-клиент, refresh mutex и обработку error envelope.
3. Заменить заглушки в `userStore`, `dictionaryStore`, `translateStore`.
4. Добавить восстановление сессии при старте.
5. Перевести аватар на multipart.
6. Добавить `isSelectedForRepetition` в тип.
7. Удалить реквизиты БД из `index.vue` и устранить дублирование `/` и
   `/exercises`.
8. Настроить `VITE_API_BASE_URL` отдельно для browser и Android.

**Проверки:** web и Android smoke test, offline/timeout, истечение access token,
повторный refresh, logout и перезапуск приложения.

### Этап 8. Hardening и готовность к эксплуатации

1. Структурированные логи без PIN, токенов, `variants` и multipart body.
2. HTTPS, trusted proxies, production CORS и secure headers.
3. Backup/restore PostgreSQL и storage, проверка восстановления.
4. Метрики ошибок, latency, rate limit и очередей.
5. Seed только для development; production import отдельной командой.
6. Нагрузочные проверки dictionary search и конкурентного complete.
7. Runbook миграций, rollback и ротации секретов.

## 6. Рекомендуемые правила для подтверждения

Принятые решения:

- `email` исключается из backend-модели и frontend DTO до появления реального
  сценария использования.
- `code` не принимается API до определения его назначения.

Ожидают подтверждения:

1. Exercise содержит максимум 10 записей: ручные имеют приоритет, остаток
   заполняется автоматически.
2. `repeatCount` увеличивается один раз на словарную запись за полностью
   завершённую двунаправленную сессию.
3. Повторение успешно, только если оба направления завершены без подсказок,
   пропусков и ошибок и с одной попытки; иначе оно считается неуспешным.
4. Ручная запись удаляется из очереди после успешного завершения сессии;
   при брошенной/ошибочной сессии остаётся в очереди.
5. Текущий PIN обязателен при смене PIN.
6. `dictionaryWordsPerPage` остаётся локальной настройкой MVP.

## 7. Приоритет поставки

Критический путь:

`решения → foundation → auth → dictionary → repetition queue → exercises → frontend integration → hardening`.

Профиль/аватар можно разрабатывать параллельно словарю после завершения
авторизации. Каждый этап должен поставляться с миграциями, OpenAPI-изменением,
Feature tests и обновлением документации.
